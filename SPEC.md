# SPEC — Madrid synthetic data generation

Spec for the **data-generation step only**: build the three CSVs that feed the series
"Let's Build Uber's Algorithm" and the terminal simulator. The ML pipeline (parts 1–8)
and the simulator will have their own specs.

Status: **awaiting approval**. Date: 2026-09-23.

> **Revision 2 (2026-09-23) — driver-centric ride simulation.** Rides are no longer
> independent, uniformly-timestamped events. They are now generated by a **day-by-day,
> 12-month simulation of a driver population** with realistic activity and churn (§2.6),
> and a new `drivers.csv` table (§2.1b) is added. Each ride carries a `driver_id`. The
> **price formula (§2.4) is unchanged** and a driver's identity **does not** affect price —
> `driver_id` is metadata (an identifier / weak distractor), never a signal feature. The
> R² ≈ 0.85 band and byte-reproducibility guarantees are preserved (NOISE_STD is
> re-calibrated because the temporal ride distribution is no longer uniform).

---

## 1. Objective

Generate, **reproducibly and offline**, a synthetic dataset tailored to **Madrid** in
which a ride's price **genuinely depends** on its features, so the teaching progression
(mean → k-NN → OLS → Ridge/Lasso → CV) shows a real RMSE drop at every episode.

Four files, all in `data/raw/`, all regenerable from the seed. The three small tables
(`madrid_locations.csv`, `ride_tiers.csv`, `drivers.csv`) are **tracked in git**; the large
`rides.csv` is **gitignored** (Rev 2 ships full Madrid scale — millions of rows — so it is
regenerated on demand rather than committed):

| File | Content | Role |
|---|---|---|
| `madrid_locations.csv` | ~130 Madrid neighborhoods with real coordinates | map: A→B distance |
| `ride_tiers.csv` | 6 tiers with price parameters (EUR) | option catalog |
| `drivers.csv` | the simulated driver population (tenure, activity, home zone) | ride generator + panel structure |
| `rides.csv` | simulated 2024 rides, each linked to a `driver_id` | price-model training |

Rides are produced by a **day-by-day simulation** of the driver population over the full
2024 calendar (§2.6): each active driver does a realistic, right-skewed number of rides on
the days they work, across a tenure window that may end mid-year (churn). The total ride
count is therefore an **emergent** function of `N_DRIVERS` and the activity model, not a
fixed input (see §2.6 for the sizing knob and the shipped default).

**Non-goals:** no ML model, no simulator, no calls to ride-hailing APIs (see §6).

## 2. The three tables

### 2.1 `madrid_locations.csv` — ~130 neighborhoods

| Column | Type | Notes |
|---|---|---|
| `location_id` | int | key |
| `neighborhood` | str | neighborhood (barrio) name |
| `district` | str | district (distrito) it belongs to |
| `lat` | float | real latitude |
| `lon` | float | real longitude |

Real coordinates of Madrid's official neighborhoods (21 districts, ~130 neighborhoods).

### 2.1b `drivers.csv` — the simulated driver population

One row per driver in the year's roster. Attributes are **per-driver** (constant across
that driver's rides) and are generated by the simulation (§2.6). None of these columns
enter the price formula.

| Column | Type | Notes |
|---|---|---|
| `driver_id` | int | key (1-based); FK target of `rides.driver_id` |
| `home_district` | cat | the driver's base district (biases where their rides start) |
| `activity_class` | cat | `casual` / `part_time` / `full_time` (drives rides-per-day + days-per-week) |
| `tenure_start` | date | first active day (may be Jan 1 for incumbents) |
| `tenure_end` | date | last active day (< Dec 31 ⇒ churned mid-year) |
| `active_days` | int | number of days actually worked in 2024 |
| `n_rides` | int | total rides the driver produced in 2024 (denormalized for convenience) |
| `driver_rating` | float | 1–5 rating, **per driver** (a weak distractor, see §2.3) |

Sizing: the number of drivers is the config knob **`N_DRIVERS`** (§2.6). The shipped default
is **15,000** — Madrid's full operating roster — so `rides.csv` reaches millions of rows and is
gitignored/regenerated (see §2.6). `drivers.csv` itself stays small (~15k rows) and is tracked.

### 2.2 `ride_tiers.csv` — 6 tiers

Tiers included: **UberX, Uber Green, Uber Comfort, UberXL, Uber Black, Uber Van**.
EUR values are **plausible but invented** (not from a real source), defined as constants
in `config.py` and ordered by increasing price.

| Column | Type | Notes |
|---|---|---|
| `tier` | str | id: `uberx`, `green`, `comfort`, `xl`, `black`, `van` |
| `display_name` | str | on-screen name |
| `capacity` | int | passenger seats |
| `base_fare` | float € | base fare |
| `per_km` | float €/km | distance rate |
| `per_min` | float €/min | time rate |
| `booking_fee` | float € | fixed booking fee |
| `min_fare` | float € | guaranteed minimum price |

Proposed initial values (adjustable in `config.py`):

| tier | cap | base | per_km | per_min | booking | min |
|---|---|---|---|---|---|---|
| uberx | 4 | 1.20 | 0.90 | 0.18 | 0.90 | 5.00 |
| green | 4 | 1.20 | 0.90 | 0.18 | 0.90 | 5.00 |
| comfort | 4 | 1.80 | 1.10 | 0.22 | 1.00 | 7.00 |
| xl | 6 | 2.50 | 1.50 | 0.28 | 1.20 | 9.00 |
| black | 4 | 4.00 | 2.20 | 0.45 | 1.50 | 12.00 |
| van | 6 | 4.50 | 2.40 | 0.50 | 1.50 | 14.00 |

### 2.3 `rides.csv` — ~50,000 rides

**Signal features** (enter the price formula):

| Column | Type | Notes |
|---|---|---|
| `ride_id` | int | key |
| `driver_id` | int | FK → `drivers`; **metadata / weak distractor, NOT a price signal** |
| `timestamp` | datetime | from the day-by-day driver simulation (§2.6), not uniform |
| `pickup_location_id` | int | FK → `madrid_locations` |
| `dropoff_location_id` | int | FK → `madrid_locations` |
| `pickup_district` | cat | pickup zone |
| `distance_km` | float | haversine(A,B) × road-factor |
| `duration_min` | float | from distance and hour-dependent average speed |
| `tier` | cat | service tier |
| `hour` | int | 0–23 (from timestamp) |
| `day_of_week` | cat | 0–6 (from timestamp) |
| `month` | int | 1–12 (from timestamp) |
| `surge_multiplier` | float | **non-linear** in hour/day (part 5) |
| `price_eur` | float € | **target** |

**Weak features / distractors** — true coefficient = 0, values sampled from the
empirical distributions of `ncr_ride_bookings.csv` (part 7, Lasso must zero them out):

| Column | NCR source |
|---|---|
| `payment_method` | `Payment Method` (per-ride) |
| `driver_rating` | **per-driver** (from `drivers.csv`), range calibrated to NCR `Driver Ratings`; joined onto each ride so it is constant within a driver |
| `customer_rating` | `Customer Rating` (per-ride) |
| `avg_vtat` | `Avg VTAT` (per-ride) |

**Data-leakage trap** (part 8) — a column derived from the target, documented:

| Column | Definition |
|---|---|
| `commission_eur` | `0.25 × price_eur` + negligible noise (Uber's cut). If included among the X features, R² jumps to ~1 → a concrete leakage example to remove. |

### 2.4 Ground-truth price formula (documented)

For each ride, using its `tier` parameters:

```
ride_base  = base_fare + per_km * distance_km + per_min * duration_min
price_raw  = ride_base * surge_multiplier + booking_fee
price_eur  = max(min_fare, price_raw + gaussian_noise)
```

- `surge_multiplier`: the **single** time-of-call mechanism (§2.5). It is a **non-linear**
  function of hour + day-of-week times a random real-time jitter. This is what makes a
  Saturday 02:00 ride much pricier than a Wednesday 11:00 ride of the same distance/tier.
- `gaussian_noise`: standard deviation **tuned** so that OLS on the signal features
  reaches **R² ≈ 0.85** (test band: **0.83–0.87**).
- The weak features and `commission_eur` **do not** enter this formula.

### 2.5 Temporal demand profile (time-of-call pricing)

`surge_multiplier = demand_profile(hour, day_of_week) × jitter`, clamped to `[1.0, 3.0]`.

- `demand_profile(hour, day_of_week)`: a documented, deterministic table giving the
  **average** surge for each time bucket. Representative levels (final values in
  `config.py`):

  | Time bucket | Example surge |
  |---|---|
  | Weekday off-peak (10–12, 14–17) | ~1.00 |
  | Weekday morning rush (7–9) | ~1.35 |
  | Weekday evening rush (18–20) | ~1.45 |
  | Weekday late night (0–5) | ~1.10 |
  | Sunday daytime | ~1.05 |
  | **Fri & Sat nights (21–03)** | **~2.2 (the expensive case)** |

- `jitter`: multiplicative random noise (e.g. lognormal centered on 1.0) representing
  minute-to-minute demand swings — so two identical trips at the same hour still differ.
- The **non-linearity** across the day (flat off-peak, sharp weekend-night peak) is
  exactly what part 5 (polynomial expansion) exists to capture: a linear hour term can't
  fit a peak that sits in the middle-ish of the 0–23 range.
- This single mechanism replaces the previous overlapping `night_weekend_factor`.

### 2.6 Driver population & day-by-day ride simulation

Rides are generated by simulating a **population of drivers over every day of 2024**,
instead of drawing independent uniform events. This makes the ride log realistic (one
driver has many rides; rides cluster on the days a driver works and at busy hours) while
keeping generation offline, deterministic, and byte-reproducible from the seed.

**Research basis** (documented in the plan; figures are approximate and platform-published
or academic):
- Madrid has ~8,900 VTC licenses but only ~3,700–4,000 *operating at any moment*; far more
  unique drivers appear across a **full year** because of high churn.
- Rides on a working day: part-time ≈ 6–12, full-time ≈ 20–25 (~2 trips/hour).
- Activity is heavily right-skewed: ~80% of drivers work <20 h/week and **>50% only
  1–5 h/week** — most drivers work a day or two per week, not daily.
- Churn is high: ~68% of drivers quit within 6 months and ~50% within a year (Stanford/Uber
  study, 1.87M drivers). This motivates staggered tenures ("3 months then change job" vs.
  "the full 12 months").

**Model.**

1. **Roster & churn (tenure).** Generate `N_DRIVERS` drivers. Each is assigned an
   `activity_class` (right-skewed: mostly `casual`, some `part_time`, few `full_time`) and a
   **tenure window** inside 2024 drawn from a cohort mixture (~3-month, ~6-month, and
   full-year cohorts, with per-driver jitter). Start dates are **staggered** (incumbents plus
   new joiners) so the count of active drivers is roughly **stationary across the year** — no
   January cliff. A driver whose window ends before Dec 31 has **churned**.

2. **Per-day activity (part-time skew).** For each driver and each calendar day **inside
   their tenure window**, the driver works that day with a probability set by their class
   (casual ≪ full_time), modulated so weekends are somewhat busier. On a worked day the
   driver produces `n ~ Poisson(class mean)` rides, `n ≥ 1` (class means chosen to hit the
   6–12 / 20–25 ranges above).

3. **Per-ride draws.** Each ride gets a **timestamp** whose hour is drawn from a documented
   per-day-of-week **hourly volume profile** (busy at commute peaks, evenings, and weekend
   nights; sparse in the small hours) — so rides realistically concentrate when demand is
   high. Origin/destination, tier, jitter and price noise are drawn per ride as before; the
   **pickup is biased toward the driver's `home_district`**. Price is computed by the
   **unchanged** formula of §2.4 — **`driver_id` never enters it**.

4. **Ordering & keys.** All generated rides are sorted by `timestamp` and assigned a unique
   sequential `ride_id`. `drivers.csv` records each driver's realized `active_days` and
   `n_rides`. Draw order is fixed so the same seed ⇒ identical `drivers.csv` **and**
   `rides.csv` (byte-identical).

**Sizing knob & the shipped default.** The number of drivers is the config constant
`N_DRIVERS` (CLI `--n-drivers`); the total ride count is emergent. Because realistic activity
means **hundreds of rides per driver per year**, the three goals {full 15k roster, realistic
per-driver activity, small CSV} are mutually exclusive — 15k drivers ⇒ *millions* of rows
(hundreds of MB / GB). The **shipped default** (decided at approval, 2026-09-23) is
**`N_DRIVERS = 15000`** — Madrid's full operating scale, yielding **millions of rides**.
Because the resulting `rides.csv` is hundreds of MB, it is **gitignored** and regenerated on
demand; the three small tables (`madrid_locations.csv`, `ride_tiers.csv`, `drivers.csv`) stay
committed. The exact row count and the re-calibrated `NOISE_STD` are fixed during calibration
(Task 3R.5) and recorded in `config.py`. Anyone can dial the scale down with `--n-drivers` for
faster iteration; R² is ~invariant to N, so a smaller count still lands in the band.

**Invariants preserved.** Every ride still satisfies §2.4 (`price ≥ min_fare`, etc.); the
pinned OLS feature set (§5.6) is unchanged and **excludes** `driver_id`; OLS R² stays in
`[0.83, 0.87]` after re-calibrating `NOISE_STD` for the new (non-uniform) temporal
distribution; and the time-of-call effect (§5.9) still holds.

## 3. Commands

```bash
pip install -e ".[dev]"          # install with dev dependencies (pytest)
python -m uber.generate_data     # generate the 4 CSVs in data/raw/
python -m uber.generate_data --seed 42 --n-drivers 1500   # optional overrides
python -m uber.generate_data --n-drivers 15000            # full Madrid scale (millions of rides!)
pytest                           # run the validation suite
```

`generate_data` accepts optional flags: `--seed`, `--n-drivers`, `--out-dir`; defaults live
in `config.py`. (`--n-rides` is replaced by `--n-drivers`: the ride count is now emergent.)

## 4. Project structure

**Lightweight modules** with separation of concerns (pure domain with no I/O; pandas/IO
isolated):

```
uber/
  entities.py       # dataclasses: Location, RideTier, Driver, Ride  (pure, no I/O)
  pricing.py        # price formula + geo (haversine, road-factor, speed-by-hour) — pure functions
  sampling.py       # seeded RNG primitives (OD pairs, tiers, jitter, hour-of-day, empirical NCR)
  simulation.py     # day-by-day driver simulation: roster + tenure/churn + per-day rides (pure, seeded)
  io.py             # CSV read/write via pandas (the single I/O point)
  generate_data.py  # orchestration + CLI entry point (python -m uber.generate_data)
  config.py         # constants: tariffs, seed, n_drivers, activity/tenure params, paths, R² band, NCR path
tests/
  test_generation.py   # validation suite (§5)
data/raw/           # output: madrid_locations.csv, ride_tiers.csv, drivers.csv, rides.csv (tracked in git)
```

Note: `uber/io.py` is imported as `uber.io` (a submodule) — it does not shadow the stdlib
`io` thanks to absolute imports.

## 5. Testing strategy

Full **pytest** suite in `tests/test_generation.py`. Assertions:

1. **Reproducibility** — same seed ⇒ byte-identical output (or equal DataFrames).
2. **Integrity** — no nulls; expected columns and types; row count consistent with
   `N_DRIVERS` and the activity model (emergent, well above 50k at the default).
3. **Price constraints** — `price_eur > 0` and `price_eur ≥ min_fare` of the tier.
4. **Geographic consistency** — `distance_km` compatible with the haversine of the two
   `location_id` coordinates; `duration_min > 0`.
5. **Tier ordering** — for an equivalent ride, mean price ordered uberx ≤ … ≤ van.
6. **Signal band** — OLS on the signal features gives **R² ∈ [0.83, 0.87]**.
7. **Useless distractors** — the weak columns have correlation ≈ 0 with `price_eur`.
8. **Leakage trap** — including `commission_eur` pushes R² ≈ 1 (verifies the trap).
9. **Time-of-call pricing** — for equivalent trips (same distance band and tier), the
   mean price on a Fri/Sat night (21–03) is materially higher (e.g. ≥ 50%) than on a
   weekday late morning (10–12). Confirms the temporal demand profile bites.
10. **Driver panel structure** — `rides.driver_id` is a valid FK into `drivers.csv` (every
    id present); many drivers have multiple rides; the per-driver ride-count distribution is
    right-skewed; and `driver_id` is **not** in the pinned OLS feature set (so it can't leak
    signal). Correlation of `driver_rating` with `price_eur` ≈ 0 (it's a distractor).
11. **Tenure / churn** — a non-trivial fraction of drivers have `tenure_end` before Dec 31
    (churned), tenures span the ~3/6/12-month cohorts, and the count of *active* drivers is
    roughly stationary month-to-month (no January cliff).
12. **Year coverage** — rides span all 12 months of 2024 and all 7 days of the week; ride
    hours concentrate at the busy buckets per the hourly volume profile (not uniform).

`pytest` added as a dev dependency under `[project.optional-dependencies].dev`.

## 6. Boundaries

**Always**
- Fixed, configurable RNG seed → **reproducible** generation.
- Document the **ground-truth price formula** in `pricing.py` and in this spec: it is the
  "answer" the models must reconstruct.

**Never**
- Call Uber or other ride-hailing service APIs.
- Commit real fare data scraped from such services.
- Generation stays **100% offline**.

**Flexible** (no approval required, but note it in the commit)
- Changes to the CSV schema, the tier list, or the R² band.
- Adding dependencies beyond numpy/pandas (default: only those + pytest dev).

## Locked decisions (from the questions)

- Scope: **data generation only** (3 CSVs + generator).
- Tariffs: **plausible invented**, EUR; distances in km.
- Tiers: **6** (uberx, green, comfort, xl, black, van).
- Signal: **OLS R² ≈ 0.85**.
- Teaching hooks: **non-linear surge + weak distractors + leakage trap**.
- NCR: **sample the empirical distributions** of its columns for the distractors.
- Locations: **~130 neighborhoods** with real coordinates.
- Distance: **haversine × road-factor**, offline/deterministic.
- Size: **emergent from `N_DRIVERS`** (Rev 2); **default `N_DRIVERS = 15000`** = full Madrid
  operating scale ⇒ millions of rides; tunable down via `--n-drivers`; horizon **2024**
  simulated **day-by-day**.
- Rides: **driver-centric** (Rev 2) — a `drivers.csv` population with tenure/churn drives a
  day-by-day simulation; each ride has a `driver_id`. **Driver is metadata, not a price
  signal** (price formula §2.4 unchanged; `driver_id` excluded from the OLS feature set).
- Architecture: **lightweight modules** (adds `simulation.py`).
- Output: **all 4 CSVs in `data/raw/`**; the 3 small tables tracked in git, **`rides.csv`
  gitignored** (Rev 2, full-scale) and regenerated from the seed.
- Tests: **full pytest suite**.
- Boundaries: **no external APIs / no scraped data**; **always seed + documented formula**.
